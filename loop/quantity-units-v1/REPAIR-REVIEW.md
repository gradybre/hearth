# REPAIR-REVIEW - quantity units v1 (independent, read-only)

Independent verification of the repairs made after CORE-REVIEW and SURFACES-REVIEW. I did not author the candidate and did not author either prior report. Nothing here was run, built, deployed or tested: every statement below is read off the supplied source, and anything that cannot be read off it is listed as unverifiable rather than as a pass.

No source edits are made here.

Out of scope by instruction, and deliberately not re-examined: the planned-meal serving context (D29) work, logging and snapshot review, the scan controller beyond the specific slot-isolation repair, small-screen render evidence, and deterministic/static/regression gates owned elsewhere. Per D26 I make no suggestion about deriving a density from zero-macro serving rows, and I do not revisit the unit-identity staleness condition beyond confirming client and server agree.

## Verified fixed

**1. Unusable stored density no longer blocks the reviewed package fallback.** `Food._usableDensity` (finite and greater than zero) now gates `ownGramsPerMillilitre`, so a stored 0, negative or NaN is ignored and `effectiveGramsPerMillilitre` falls through to `packageGramsPerMillilitre` as R12 requires. `packageDensityConflictsWithOwn` reads the same accessor, so the 5% warning cannot be computed against a figure nothing can divide by. `FoodDraft.usablePreservedDensity` mirrors the rule in the editor, and `toFood` writes the usable value only, so a malformed density is not re-persisted by an ordinary rename while the source-stated density it carries is preserved.

**2. Malformed records are no longer attached to outgoing payloads.** `PackageNutrition.isSendable` is consulted by `FoodMapper.toJson`: the `package_nutrition` key is written when the relation is null (an explicit removal, which must propagate) or sendable, and omitted otherwise. An omitted key is silence, which the upsert function treats as preserve-stored, so a malformed version-1 record can no longer fail the whole food upsert and strand unrelated name, macro and serving edits behind a retrying write. The record stays in the local column for correction, which is what R10 asks for.

**3. The size bound is measured on the bytes actually written.** `_encodedBytes` sizes `toJson()` - the exact map that is encoded and pushed - and takes the larger of the compact wire encoding and an estimate of the Postgres `jsonb::text` form, including the separator widths and the expansion of exponent-notation numbers. It never throws out of `isValid` or `isSendable`. The server bound is `octet_length(package_nutrition::text) > 4096`, so the client is the stricter side of the same limit, which is the safe direction. An unknown-version record is sendable when it fits, which is correct: it arrived from a server that stored it and is round-tripped verbatim.

**4. Forward compatibility on unrelated saves.** `toJson` now returns `Map.of(rawJson)` for any parsed record, not only unknown versions, so extension keys a newer client wrote inside a version-1 record survive an unrelated edit made on this build. Records built by `PackageNutrition.manual` have an empty raw map and serialise from their typed fields, so both paths still produce the documented shape.

**5. Prepared and drained capture facts are durable, and the record still cannot activate an unreviewed basis.** `FoodDraft.confirmPackageNutrition` embeds a `capture` object inside the same version-1 record carrying the label's own `basis`, per-field `field_sources`, `reviewed_same_basis` and the bounded review `notes`; the notes are preserved rather than cleared on confirm. `FoodDraft.fromFood` and `fromLookup` read all four back through `_captureBasis`, `_captureFieldSources`, `_captureReviewed` and `_captureNotes`, so a reopened food still shows what the panel said and what was acknowledged, with the original facts available for correction. Activation remains gated: `packageNutritionError` refuses to confirm while a basis warning is unacknowledged, and `withLabel` clears a prior acknowledgement whenever a fresh unsafe scan arrives, so an answer given about one pair of photos cannot carry to another. `fromLookup` copies the capture only alongside the exact basis it describes, and only with a remapped id for a relation that was active on the source food.

**6. Exact source quantities are preserved.** `ServingDraft.resolvedAmount` returns the loaded `Quantity` while the field text is unmodified, `FoodDraft.toFood` does the same for the pack size against `originalPackSize`/`originalPackText`, and `withLabel` carries a photo-read pack's own canonical amount beside its formatted text rather than re-parsing the string. So an unchanged 14.5 oz or 15.25 oz round-trips as stored, and a relation anchored to a serving is not made stale by a rewrite nobody asked for.

**7. The shopping amount sheet reads derived values and writes original ones.** `ShoppingLineResolver.resolve` is used for display only. `_read` returns the stored quantity whenever the field text is unmodified, so an untouched on-hand figure is written back as the stored value and not as the resolver's converted view; an untouched Buy field leaves `widget.line.wanted` exactly as it was, including the case of no decision at all. `_asOverride` compares a typed value against the settled planned amount, so retyping the recipes' own number does not mark the line edited. No ask or contribution is mutated here.

**8. Label photo roles are whitelisted and advisory.** `labelPhotoRoles` accepts only an array whose length matches the image count and maps only the two known role strings into fixed prompt text; anything else contributes an empty string. The client sends `image_roles` only in label mode, in the same fixed back-then-front order as the images. `field_sources` is narrowed to three known keys with four allowed values on the server and again on the client. Roles remain hints, and the transcribed facts still come from the images.

**9. Scan slot isolation and single delivery.** `LabelScanController` keeps one generation per slot in `_picks`, so an operation on one slot can no longer silently discard an in-flight pick for the other, while `remove` and `pick` still invalidate the single combined `_read` generation - which is correct, because the read was sent for photos that have changed. `_ReadLabelSheetState._delivered` makes the done-frame pop one-shot, so two builds inside one frame cannot pop the editor route as well.

**10. Manual edits after a photo read re-mark provenance.** `FoodDraft.copyWith` routes through `_sourceAfterEdit`, so editing the package amount text or any serving moves a `photos` record to `mixed`; `withPackageField` does the same for the count, serving selection and the approximate qualifier. This was listed as a pending item in the prior surfaces report and now appears handled on both paths.

**11. Remove is reachable before confirmation.** The editor renders the remove-link action when `originalPackageNutrition != null || hasEnteredPackageFields`, so a photo-suggested serving that produced a field error can be cleared by the control the save-time message points at, rather than only by emptying the count field.

**12. Unit agreement between client staleness and server membership.** `PackageNutrition._sameQuantity` requires the preferred unit to match, and the upsert function's snapshot check compares `amount_unit` against the snapshot `unit` and `amount_kind` against `kind` before comparing the number with a relative tolerance and absolute floor. The two sides agree, which was the condition the prior report attached to accepting this behaviour. No action.

## Remaining actual blockers

### R1 (High) - confirm can silently do nothing while Save stays blocked, losing a reviewed scan relationship

`FoodDraft.confirmPackageNutrition` returns `this` unchanged in two reachable cases, with no message anywhere:

- **Overflow count.** `packageNutritionError` accepts any finite positive `servingsPerPackage`. With a large count (for example 1e308) against a cup serving, `serving.canonicalAmount * count` overflows, so `_impliedGramsPerMillilitre` is null and `isValid` is false - correct, and the L11 repair - but `packageNutritionError` is still null, `packageNutritionNeedsConfirmation` is true and the confirm button is rendered. Tapping it changes nothing. `_save` then refuses the whole food with `packageNutritionNeedsConfirmation`, showing text that asks the user to confirm or remove. Confirming is impossible, so the only escape is the remove link, and nothing explains why.
- **Oversize capture.** `_boundedNotes` caps six notes at 200 UTF-16 units each. Note text is assembled from model-supplied `issue.field` and `issue.note`, so multi-byte or heavily escaped content can carry the captured record past the 4 KiB cap even when the un-captured `relation` is comfortably valid. `captured.isValid` is then false and the same silent `return this` fires - a reviewed, otherwise valid, scan-derived relationship is lost at the moment of confirmation, and Save is blocked in the same way.

Narrow fix: report a field-level explanation whenever a complete entry cannot produce a usable relation (so the count case reads as bad input rather than a dead button), and on the capture path fall back to the valid `relation` - or to a capture carrying only `basis`, `field_sources` and `reviewed_same_basis` - rather than abandoning the confirmation entirely. Bounding notes by encoded bytes rather than by UTF-16 length would remove the size path altogether.

### R2 (Medium) - note truncation and an over-eager basis warning

Two smaller issues in the same area, reported together because one fix touches both:

- `_boundedNotes` truncates with `substring(0, 200)` on UTF-16 units, which can split a surrogate pair. The lone surrogate survives into the persisted record and is replaced on encode, so the stored evidence can contain a replacement character mid-word. Truncating on a rune boundary, by encoded length, fixes this and R1's size path at once.
- `withLabel` raises the manual-confirmation note whenever `reading.packageBasis != 'as_packaged'`. Both the server default and `EdgeFunctionLabelReader._basis` clamp a silent or unrecognised panel to `unknown`, which is the ordinary case, so nearly every scan that supplies a package amount or a serving count demands the preparation tick. That is a warning the user cannot honestly clear, and it gates confirmation. Distinguishing an unstated basis from an explicitly prepared or drained one would keep R9's protection where it belongs.

## Unverifiable from the supplied source

Listed so they are not mistaken for passes.

- **Highest residual risk.** `QuantityMapper.kindToSql` was not supplied. The upsert function compares a serving row's `amount_kind` against the snapshot's `kind`, and the snapshot is written from `Quantity.kind.name` (`mass`, `volume`) while the serving row is written through `kindToSql`. If those two strings ever differ, every newly confirmed relation raises `check_violation` and takes the whole food upsert with it - the same class of sync stall the B4 repair was made for, arriving from the other side. One fixture comparing the two writers would settle it.
- Unit identifiers. The server whitelists specific mass and volume unit strings; `Units` was not supplied, so I cannot confirm that every unit the serving dropdown and pack parser can produce appears on those lists. A missing spelling refuses a record the user has already reviewed, and it surfaces as an opaque sync failure.
- `macro_calculator.dart`, `portion_unit.dart`, `log_sheet.dart`, `unit_converter.dart`, `food_quantity_format.dart`, `quantity.dart`, `library_sync.dart`, the Drift schema and the generated history were not supplied. So: downstream NaN behaviour beyond the `ownGramsPerMillilitre` gate, cross-kind portion offering, coverage and snapshot behaviour, the display unit the amount sheet picks versus the one the list row prints, `Quantity` value equality (which `withLabel`'s conflict note depends on), omitted-key versus explicit-null handling in pull, and the local v29 upgrade are all unchecked here.
- Recipe surfaces (grouped, combined, scaled, step amounts, cook-along) and the export preview were not supplied in this packet, so the prior report's combined-row raw-source finding is neither confirmed nor cleared.
- No image, device, database or function evidence was available, so nothing about render, migration application or live extraction is asserted.
