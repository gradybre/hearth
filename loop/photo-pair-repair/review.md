=== NEW OBSERVATIONS THIS ROUND (all low; none blocking) ===

N1 (low, wording). The M1 failure message is 'No package size came off that photo…', but the throw fires whenever the *gated* reading is empty — which is `servings.isEmpty && packageSize == null && servingsPerContainer == null && !walmartLink.hasLink`. A reply that carried a servings-per-container count but no net weight would not reach the throw at all (correct), but a reply that carried nothing but nutrition and a *name* also throws with a message naming only the package size, since `isEmpty` ignores name and brand. That is a pre-existing property of `isEmpty`, not a new defect, and the message's advice ('add the nutrition panel photo too') is still the right next action in every case that reaches it. No change needed; recorded so the wording is not mistaken for a precise diagnosis.

N2 (low, prompt change outside the original finding set). LABEL_PROMPT's final paragraph was rewritten this round from 'transcribe your best reading AND list it in uncertain' to 'omit that figure entirely and say in uncertain which one it was'. This is a real behavioural change to extraction that none of my findings asked for, and it is in tension with EXTRACT_PROMPT and MENU_PROMPT, which both still instruct best-reading-plus-flag. For a label I think the new rule is defensible and arguably better — a half-read macro lands on a review screen looking exactly like a checked one, and §5.6 already has a first-class representation for 'unknown' in the minor three — and the paragraph explicitly protects the legible facts beside the unreadable one. But three consequences deserve naming: (a) the four major macros have no 'unknown' representation downstream, so an omitted kcal becomes a stated zero via `?? 0` in both the server shaper and `ServingDraft._field`, which is a *worse* silent claim than a flagged best guess; (b) a row omitting `kcal` entirely is refused by the tool schema's `required: ['amount','unit','kcal']`, so the whole row is likely lost rather than partially read; (c) it diverges from the two sibling prompts without a comment saying why. This is the one change in the round whose user-visible effect I cannot predict from reading, and it is unmeasured because it is prompt behaviour. Recommend either reverting to best-reading-plus-flag for the four majors while keeping omit-and-flag for the minors, or adding a comment recording the deliberate divergence — and in either case, exercising it in the pending live run with a deliberately blurred figure.

N3 (low, unchanged from before, now moot in practice). `key: ValueKey<String>(_draft.servings[i].id ?? 'row-$i')` in food_editor_screen.dart could collide if a row carried the literal id 'row-1' alongside a null-id row at index 1. Contrived, and every production path now assigns a Uuid at row creation. No action.
